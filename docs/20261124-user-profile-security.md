# ユーザー設定とフレンド検索用プロフィールの分離

## 変更の意図

メールアドレスなどの個人情報を本人専用に保ち、フレンドID検索に必要な情報だけを別ドキュメントで扱う。例えばユーザーBがAを検索すると、AのユーザーIDと表示名だけを取得し、メールアドレスを含む設定へのアクセスは拒否される。

## 保存先とアクセス権

| 保存先 | 保存項目 | 読み取り | 書き込み |
| --- | --- | --- | --- |
| `users/{uid}` | 表示名・メール・プロフィール画像などの設定 | 本人のみ | 本人のみ |
| `publicProfiles/{uid}` | `userId`, `displayName` の2項目のみ | UIDを指定した認証済み利用者 | 本人のみ |

`publicProfiles` の一覧取得と、メール等の追加フィールドの保存は拒否する。ここで「公開」はアプリの認証済み利用者向けであり、匿名公開ではない。

`setUserSettings` は2つのドキュメントを同じバッチで更新する。部分更新時もメールや作成日時を維持し、公開先には許可した2項目だけを明示的に書き込む。ログイン時にも公開プロフィールを同期する。フレンド検索は `publicProfiles` だけを参照する。

ユーザー情報用ポリシーは `firebase/user-profile.rules` に保存した。これは対象部分のポリシーなので、単体で本番全体へデプロイせず、取得した既存ルールの該当部分に統合する。既存の他コレクションのアクセス条件は今回の変更に含めない。設定例も `FIREBASE_SETUP.md` に反映した。

## 検証

- Firestore Emulatorで39ケースを確認。匿名・本人・他人の各操作、一覧取得の拒否、公開先へのメール混入・所有者偽装等の拒否を含む。
- 実際のデータアクセス関数をエミュレーターにつなぎ、新規作成、部分更新、別アカウントのフレンド検索と個人設定の読み取り拒否を確認。
- 本番へ反映する統合ルールでも同じテストが成功。他コレクションのルールが取得時から変わっていないことを確認。
- 変更ファイルのESLintはエラーなし。AuthContextには既存の未使用変数の警告が1件ある。
- `pnpm run build:web` が成功。
- 既存10ユーザーの公開プロフィールを追加し、保存先の全項目が `userId` と `displayName` のみであること、表示名が移行元と一致することを確認。元の個人設定は変更していない。
- リポジトリ全体の型検査は既存エラーで失敗。変更前コミットの別ディレクトリでも再現し、今回の変更箇所に新しい型エラーは確認していない。

テストの再実行にはJava、Firebase CLIとpnpm依存関係が必要。`pnpm test:firestore` を実行する。実際のFirebaseプロジェクトへの接続は使わず、`demo-readeco-users-security` で実行する。

## 本番への反映手順

1. Firebase MCPで稼働ルールを取得してローカルにバックアップ。
2. 公開プロフィール部分のルールを追加し、移行とアプリの切り替えを先に行う。
3. 既存ユーザーの表示名だけを取得し、ユーザーIDと表示名を公開先に移行。メールや画像は移行しない。
4. アプリを更新し、Webの配信更新を確認してからユーザー設定の本人限定ルールを反映。
5. Firebase MCPで最終ルールを再取得し、未認証の設定アクセス拒否を本番で確認。

本番の既存ユーザーデータはテスト用に変更・削除しない。移行は公開先への追加のみを行う。旧版を開いたままのWeb利用者は更新後に再読み込みが必要。インストール済みモバイル版を配布している場合も、新しい検索先を使用するアプリ更新が必要。

本番の反映結果と取得した統合ルールは、公開リポジトリに他コレクションの設定を載せないよう、ローカルの診断記録で管理する。
