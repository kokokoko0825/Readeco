# エージェント向け：リリース・告知の運用

## 目的と正本

利用できる変更を、読書を妨げずに伝え、過去の変更も確認できる状態を保つ。

- 告知原稿：`constants/release-notes.json`。型と表示用の種別名は `constants/release-notes.ts`。
- アプリの版：`package.json` の `version`。`app.config.ts` がExpo設定へ、`constants/app.ts` が画面へ渡す。`app.json` へ版を重複記載しない。
- 履歴画面：`app/updates.tsx`。設定 → リリースノート、または `/updates`。告知だけはログインせずに読める。
- 新着管理：`contexts/ReleaseNotesContext.tsx` と `utils/release-notes-store.ts`。
- PWA：`web/service-worker.js` はテンプレート。`build:web` の最後に配信ファイルの内容からキャッシュ名を生成する。手動の `v9` 等は不要。

告知はアプリに同梱する。CMSや外部Widget、サーバー側の既読保存は使わない。GitHub Releaseも下記コマンドで同じ原稿から生成し、別の本文を手で維持しない。

## 変更時に判断すること

利用者の操作や結果が変わる新機能、意味のある改善、不具合修正を掲載する。内部整理・テスト・依存の更新のみなら原稿は不要。すべてのPRに告知ファイルや版上げを義務付けない。

開発中はPR本文に利用者への影響をメモし、公開するPRで文章をまとめる。通常の機能変更はそのPRで原稿を完成させ、複数PRをまとめる必要がある時だけ公開用のPRを別に作る。未実装の内容、未来の予約原稿、秘密値や未修正問題の攻撃手順を本番同梱の配列に入れない。

技術的な版を上げる必要がある時だけ `package.json` を編集する。告知に対応版を載せる場合も、アプリ版との一致を表示条件にしない。

## 原稿の追加

新しい告知をJSON配列の先頭に追加する。これは形式例であり、未実装の機能をそのまま転記してはいけない。

```json
{
  "id": "20261126-title-search",
  "sequence": 9,
  "title": "タイトルの一部から本を探しやすくなりました",
  "date": "2026-11-26",
  "notification": "badge",
  "changes": [
    { "type": "improved", "text": "タイトルの一部でも、探している本を見つけやすくなりました。" }
  ]
}
```

- `id`：不変かつ一意。半角英数字・ハイフン・ドット。公開後は使い回さない。
- `sequence`：正の整数。公開済み最大値より大きくする。配列は降順。同日の複数告知もこの順序で扱う。
- `title` / `changes[].text`：利用者の操作・結果が分かる日本語のプレーンテキスト。HTMLやMarkdownは実行・解釈しない。
- `date`：実際の公開予定に合わせた日付を `YYYY-MM-DD` で指定。公開時に実際の配信日と確認する。
- `version`：対応する技術的な版を `1.1.10` のように任意で付ける。複数告知が同じ版でもよい。
- `notification`：意味のある変更は `badge`。控えめな小修正は `none` とし、履歴だけに掲載する。
- `changes[].type`：`added`（新機能）、`improved`（改善）、`fixed`（修正）、`removed`（提供終了）。1件以上。

例：「stale query invalidationを修正」ではなく「本を更新しても一覧が古いままになる問題を修正しました」。種別はUIが表示するので本文の先頭に「修正:」を重ねない。

公開済みの記事を消したり、再通知目的でID・sequenceを変えたりしない。誤字の修正は同じIDでよい。利用者に影響する訂正・機能の取り消しは、新しい告知を追加する。初期移行した `legacy-*` のID、順序、日付、対応版も維持する。

## 新着と確認位置

自動モーダルは表示しない。`badge` の告知が未確認なら設定タブとリリースノート項目に「新着」を表示する。履歴を実際にレイアウトし、画面がフォーカスを得た後に、そのビルドに含む最新sequenceまで確認したものとして保存する。精読の証明や個別記事の読了管理ではない。

保存先は端末ローカルのAsyncStorage、キーは `@readeco_release_notes_seen:<Firebase UID>`。別アカウントと共有せず、端末間では同期しない。ブラウザーの保存データを消すと確認位置も失われる。

- 初回利用：最新位置を基準にし、過去分を未読として積まない。
- 移行：旧キー `@readeco_last_seen_version` が既知の版なら、その告知の位置を一度だけ引き継ぐ。旧キーは元々アカウント共通なので、個人の読了を保証する値ではない。未知・壊れた旧値は最新位置から始める。旧キーはロールバック互換のため削除・更新しない。
- ロールバック：例えば10まで確認した利用者が8までのビルドに戻っても、保存値10を8へ下げない。後に11を公開した時だけ新着になる。
- 保存失敗：成功したふりをして新着を消さない。履歴の閲覧は継続できる。初期化自体に失敗した場合は再読み込みで再試行する。

実装変更時は、画面を開く予約だけで確認位置を進めないこと、別UIDの遅延処理で現UIDの状態を上書きしないことを保つ。

## 公開前の確認

Node.js 24を推奨（単体テストのTypeScript型除去には22.18以降が必要）。依存の管理はpnpmを使う。

```sh
pnpm run check:releases
pnpm run test:releases
pnpm run build:web
```

`check:releases` はIDの重複、順序、日付、本文、種別、通知値、版の重複設定を検証する。毎デプロイで最新告知の版とアプリ版が一致することは要求しない。GitHub Actionsの `Release notes` もPRとmain pushで同じ検証・単体テストを行う。これは告知の検証であり、本番配信ではない。

単体テストは初回、旧7版の移行、UID分離、通知なし、保存失敗、並行保存、ロールバック、不正原稿、キャッシュ生成を確認する。UIや既読管理を変えた時は、ブラウザーでも履歴全件・新着表示・履歴を開いた後の新着消去・戻る操作・モバイル幅・ダークモードを確認する。認証を迂回するコードや本番用のテストアカウントを追加しない。

## 本番への公開とGitHub Release

1. 公開する変更と原稿を同じPR・ビルドに含め、レビューと検証を通す。
2. mainへマージ／pushし、既存のmain配信経路で反映する。作業ツリーからの手元デプロイや、タグを起点とする追加の配信経路を増やさない。
3. 対象コミットSHAに対応した本番配信の成功と、実際の機能・`/updates` を確認する。「最新の配信が成功した」だけで別コミットの成功と取り違えない。
4. 技術的な節目を記録する場合だけ、同じSHAにタグとGitHub Releaseを作る。毎デプロイのタグ作成は必須ではない。

GitHub Releaseの原稿は、告知IDを指定して生成できる。

```sh
pnpm run release:notes 20261125-release-history /tmp/readeco-release.md
```

その後、確認済みの本番SHAを指定して `gh release create v1.1.10 --target <確認済みSHA> --title v1.1.10 --notes-file /tmp/readeco-release.md` を実行する。`<確認済みSHA>` は実際の値に置き換える。アプリの版を上げていない告知だけの公開では、無理に技術版タグを作らない。

本番失敗時はタグ・Releaseだけ先に公開しない。Releaseの作成のみ失敗したら同じタグ・同じSHAで再実行し、既存タグを別コミットへ動かさない。mainへ連続pushした場合は、実際に本番へ配信されたコミットと包含する変更を確認する。ロールバックは既存の配信手順で旧ビルドを戻し、旧版の告知だけが表示される状態にする。

この実装では本番配信やタグ発行をActionsで自動化していない。Cloudflareの接続先・本番ブランチ等の管理設定を確認せずに、第二のデプロイ経路や新しい秘密値を追加しない。
